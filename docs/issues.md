# Стандарт створення Issues у TYMAN

Це єдиний стандарт для людей і coding agents. Точка входу для агентів —
[AGENTS.md](../AGENTS.md). Назви й описи Issues пиши **українською**;
назви полів Project, значення, команди, ідентифікатори та шляхи залишай без перекладу.

Репозиторій: [qwer605/tyman](https://github.com/qwer605/tyman).
Проєкт: [TYMAN №2](https://github.com/users/qwer605/projects/2), власник `qwer605`.
Створюй справжнє Issue в цьому репозиторії та додавай його до цього Project.
Запит на створення завдання не означає запит на його реалізацію чи відкриття PR.
PR, включно з draft, відкривай лише за явним запитом користувача.

## Порядок створення завдання

1. Прочитай запит і відповідний код або документацію. Відокрем установлені факти
   від припущень; не вигадуй відтворення помилки чи результати перевірок.
2. Пошукай дублікати серед відкритих і закритих Issues у `qwer605/tyman` за
   суттю проблеми, назвами механік, повідомленнями помилок і пов’язаними файлами.
   Якщо таке завдання вже є, поверни посилання; змінюй його лише в межах запиту.
3. Сформулюй один перевірюваний результат на Issue. Великі незалежні частини
   розділяй, якщо запит передбачає декомпозицію. Укажи відомі залежності.
4. Створи Issue українською за відповідним шаблоном нижче. Номер наперед не вгадуй.
5. Додай створене Issue до TYMAN. Якщо воно вже додане автоматично, використай
   наявний елемент Project замість дублювання.
6. Заповни Status, Priority, Severity та інші поля за правилами нижче.
7. Повторно прочитай Issue й елемент Project: перевір назву, опис, labels,
   виконавця, членство в TYMAN і фактичні значення полів. Перевір код `TMN-<номер>`
   та стан створення пов’язаної гілки після завершення workflow.
8. Поверни посилання на Issue, його код, Status, Priority, Severity та виконавця.
   Якщо додавання до Project або автоматизація не спрацювали, повідом точний
   незавершений крок. Не створюй повторне Issue через частковий збій.

Якщо доступу до GitHub немає, підготуй назву, опис і запропоновані поля локально
або у відповіді та явно вкажи, що Issue ще не створено. Не проси надсилати токени
в чат. Для репозиторію потрібні права на Issues, для Project — окремий доступ
до Projects; у GitHub CLI з OAuth це scope `project`.

Для перевірки через GitHub CLI можна використати:

```sh
gh issue list --repo qwer605/tyman --state all --search "ключові слова" --limit 100
gh label list --repo qwer605/tyman --limit 100
gh project field-list 2 --owner qwer605 --format json
```

Використовуй доступні підключені інструменти або CLI. Перед записом отримуй
актуальні ID полів, options та елемента Project; не перенось ID з іншого проєкту.
Багаторядковий опис передавай як текстове поле інструмента або через `--body-file`.

## Назва й опис

Назва коротко описує дію та результат українською: `Додати лічильник кристалів`
або `Виправити повторне зарахування кристала`. Після створення формат має бути
`TMN-<номер>: <назва>`. Префікс додає workflow; не підставляй вигаданий номер.

Пиши так, щоб після першого читання було зрозуміло, з чого почати і що показати
як результат. Просте завдання зазвичай уміщується в 5–10 коротких рядків.
Використовуй три розділи:

- **Що потрібно зробити** — конкретна дія; за потреби одне речення, навіщо це потрібно.
- **Готово, коли** — 1–3 перевірювані результати у вигляді `- [ ]`.
- **Як перевірити** — короткі кроки або команда.

Не повторюй дію окремо в меті, обсязі роботи та критеріях. Пиши «показати модель
у сцені» замість «забезпечити можливість візуалізації». Посилання додавай там,
де вони допомагають виконати завдання; порожні розділи не потрібні.
Детальний опис додавай лише для складної роботи. Невідомі вимоги сформулюй
короткими питаннями, не вигадуй відповіді.

Для помилки також додай **Як відтворити** та коротко вкажи, що відбувається
зараз і що має відбуватися. Версію гри, Godot та ОС додавай, якщо вони відомі
або потрібні для відтворення. План перевірки не подавай як уже виконаний тест.

Ручне створення використовує ті самі розділи:
[завдання](../.github/ISSUE_TEMPLATE/task.md) та
[повідомлення про помилку](../.github/ISSUE_TEMPLATE/bug.md).

## Поля Issue та Project

| Поле | Правило |
| --- | --- |
| Repository / Project | `qwer605/tyman` / `TYMAN`, власник `qwer605`, Project №2. |
| Status | Нове завдання — `Backlog`. `Todo` — якщо його вже погоджено до роботи. `In Progress` — коли реалізація фактично почалася. |
| Priority | Заповнюй для кожного завдання. Використовуй вказаний користувачем пріоритет; якщо його немає, звичайне планове завдання має `🔸Major`. Підвищення обґрунтуй впливом або терміном. |
| Severity | Для дефекту вибери рівень за фактичним впливом. Для нової можливості, документації чи дослідження залишай порожнім. Якщо вплив невідомий, не вгадуй — зафіксуй це в описі. |
| Assignees | Призначай явно вказаного або вже узгодженого виконавця після перевірки GitHub login. Якщо виконавець невідомий, залишай порожнім; не призначай автора чи агента автоматично. |
| Labels | Використовуй наявні доречні labels: `bug` для дефекту, `enhancement` для можливості чи поліпшення, `documentation` для документації, `question` для відкритого питання. Перевір актуальний список; нові labels не створюй без запиту. |
| Milestone | Указуй лише погоджену цільову версію або milestone. |
| Залежності | Додавай посилання на відомі блокувальні та пов’язані Issues; не вигадуй зв’язки. |

Окреме поле типу завдання поки не визначене цим стандартом: це робота
[TMN-8](https://github.com/qwer605/tyman/issues/8). Не створюй нову схему типів
під час звичайного оформлення Issue. Поточні категорії передаються наявними labels.

**Priority визначає черговість роботи:**

| Значення | Коли вибирати |
| --- | --- |
| `⛔Blocker` | Блокує роботу команди або поточну обов’язкову перевірку; потрібна негайна дія. |
| `⚡Critical` | Потрібне для найближчої погодженої мети чи релізу. |
| `🔸Major` | Звичайне планове завдання. |
| `🔹Minor` | Поліпшення, яке можна відкласти. |

**Severity визначає вплив помилки на гру:**

| Значення | Коли вибирати |
| --- | --- |
| `⛔Blocker` | Гра або основний сценарій повністю заблоковані, обхідного шляху немає. |
| `⚡Critical` | Збій гри, втрата даних або недоступна ключова механіка. |
| `🔸Major` | Помітно порушено функцію чи ігровий процес. |
| `🔹Minor` | Незначний дефект; основний сценарій працює, доступний обхідний шлях. |
| `Trivial` | Косметична або текстова помилка без впливу на ігровий процес. |

Поля незалежні: не копіюй Priority у Severity автоматично. Значення в таблицях
містять фактичні emoji; через API вибирай поточний option ID із Project.
Severity показано поруч із Priority у Tasks, Backlog і My tasks.

Інші статуси: `In review` — триває review відкритого PR, `Test` — ручна перевірка
змін перед злиттям, `Done` — прийняті зміни злито. Саме створення Issue не переводить
його в `In Progress` чи `Done`. `Done` не означає випуск релізу. Обов’язкове
схвалення PR іншим учасником не вимагається.

## Приклади оформлення

Це приклади, а не повідомлення про виявлені дефекти. Номер присвоїть GitHub.

### Звичайне завдання

Назва: `Додати лічильник зібраних кристалів у HUD`.
Поля: label `enhancement`, Status `Backlog`, Priority `🔸Major`, Severity порожнє,
виконавець не призначений.

```markdown
## Що потрібно зробити
Показати в HUD кількість зібраних кристалів, наприклад «2 із 5».

## Готово, коли
- [ ] Після збору кристала число збільшується на один.
- [ ] На початку нового проходження показано «0 із 5».

## Як перевірити
Запустити гру, зібрати два кристали та почати нове проходження.
```

### Повідомлення про помилку

Назва: `Виправити подвійне зарахування одного кристала`.
Поля: label `bug`, Status `Backlog`, Priority `🔸Major`, Severity `🔸Major`,
виконавець не призначений. У справжньому Issue заповни фактичне середовище.

```markdown
## Що потрібно зробити
Виправити подвійне зарахування кристала: зараз один кристал додає 2 до лічильника,
а має додавати 1.

## Як відтворити
Почати гру, увійти в область одного кристала й залишитися в ній.

## Готово, коли
- [ ] Один кристал зараховується лише раз.
- [ ] Інші кристали теж можна зібрати.

## Як перевірити
Повторити ці кроки, потім зібрати ще один кристал і перевірити лічильник.
```


## Коди завдань і гілки

Кожне Issue в репозиторії має код `TMN-<номер Issue>` у назві. Наприклад,
Issue `#7` має назву `TMN-7: Сформувати контекст` і пов’язану гілку `TMN-7`.
Власний номер GitHub `#7` залишається без змін.

Після створення, редагування, повторного відкриття або перенесення Issue
workflow **Issue keys and branches**:

1. Додає правильний код до назви без дублювання префікса.
2. Створює гілку `TMN-<номер>` від поточного коміту основної гілки.
3. Пов’язує гілку з Issue: вона з’являється в розділі **Development**.

Автоматизація працює після злиття її PR в основну гілку. Зміни з’являються
після завершення workflow, тому одразу після створення Issue можлива затримка.
Відкрити PR із пов’язаної гілки можна звичайним способом.

Повторні запуски зберігають наявні гілки та їхні коміти. Якщо однойменна гілка
вже існує, але не пов’язана з цим Issue або його PR, workflow повідомляє про
конфлікт і не перезаписує гілку. Для закритих Issues оновлюється лише назва.

Чернетки **Draft issue** не мають номера репозиторію. Щоб отримати код і гілку,
перетворіть чернетку на Issue через **Convert to issue → qwer605/tyman**.

Для ручного запуску відкрийте **Actions → Issue keys and branches → Run workflow**.
Укажіть номер Issue або залиште поле порожнім, щоб обробити всі Issues.

Для роботи достатньо вбудованого `GITHUB_TOKEN` з дозволами `issues: write`,
`contents: write` та `pull-requests: read` для перевірки вже пов'язаних PR.
Додаткові токени в secrets не потрібні.

Перевірка логіки:

```sh
node --test .github/issues/test/sync.test.cjs
```
