# Релизы Tyman

## Что происходит автоматически

`main` объединяет одобренные изменения. Ветки `release/X.Y.Z` фиксируют состав
конкретного выпуска. Новые задачи продолжают попадать в `main`, пока RC тестируется.
Одновременно поддерживается один незавершённый выпуск.

Релиз состоит из:

- `tyman-windows-x86_64.zip` — Windows-игра и PCK;
- `tyman-linux-x86_64.zip` — Linux-игра и PCK;
- `tyman-source.zip` — исходники ровно выбранного коммита;
- `release-manifest.json` — версия, RC, SHA коммита и контрольные суммы;
- `SHA256SUMS` — SHA256 архивов.

Распакуйте архив целиком: исполняемый файл должен оставаться рядом с `.pck`.
Stable получает **те же байты**, которые были опубликованы в выбранном RC;
его манифест намеренно сохраняет имя протестированного RC.

## Первый запуск

1. Слейте PR с проектом и workflows в `main` после approval другого владельца кода.
2. Дождитесь успешного CI на `main`.
3. Откройте **Actions → Releases → Run workflow**.
4. Выберите ветку **main**, действие **prepare** и нажмите **Run workflow**.
5. После успешного запуска откройте **Releases** и скачайте архив нужной платформы.

Первый `feat:` от версии `0.0.0` создаёт `0.1.0-rc.1`. Стабильной версии пока нет.
Workflow сам создаёт `release/0.1.0`; вручную выбирать или создавать ветку не нужно.

## Как определяется версия

Release Please анализирует все коммиты после последнего стабильного тега, включая
коммиты из объединённых веток. Итоговое повышение одно на весь набор:

| Коммиты после `v1.2.3` | Следующая версия |
| --- | --- |
| Только `fix:` / `perf:` | `1.2.4` |
| Есть `feat:` | `1.3.0` |
| Есть `!` или `BREAKING CHANGE:` | `2.0.0` |

`chore:`, `docs:`, `ci:` и другие служебные коммиты сами по себе выпуск не создают.
Принудительный `Release-As` отключён. До `1.0.0` также используются обычные повышения:
например, `feat:` после `0.1.0` даёт `0.2.0`, несовместимость — `1.0.0`.

Обычный merge сохраняет несколько `fix` / `feat` коммитов одной ветки.
При squash итоговый коммит должен содержать самое значимое изменение PR. Используйте
Conventional Commit в заголовке PR и проверьте сообщение перед squash merge.
Детали нескольких изменений можно сохранить в теле итогового коммита как
Conventional Commit footers, поддерживаемые Release Please.

## Если в RC найден баг

1. Обновите `release/X.Y.Z` из основного репозитория. Fork делают один раз для репозитория.
2. Создайте от этой ветки рабочую ветку `fix/...`.
3. Исправьте баг, откройте PR **в `release/X.Y.Z`** и получите approval другого владельца кода.
4. После merge автоматически запускаются тесты и сборки, затем появляется `rc.2`, `rc.3` и т. д.

Номер `X.Y.Z` во время исправлений сохраняется. `feat:` и несовместимые изменения
в уже зафиксированном выпуске отклоняются релизной автоматикой: отправляйте их в `main`.
Старые RC и их теги не перезаписываются.

## Публикация stable

1. Проверьте **последний RC**, включая запуск и управление игрой на нужных платформах.
2. Откройте **Actions → Releases → Run workflow**, выберите **main**.
3. Выберите **publish-stable**.
4. В `candidate` укажите точный тег, например `v0.1.0-rc.2`.
5. Отметьте `confirm_tested`, только если проверен именно этот RC.

Workflow проверит, что релизная ветка всё ещё указывает на протестированный коммит,
проверит все контрольные суммы и скопирует файлы в стабильный релиз `vX.Y.Z`.
Если в ветке уже появились новые изменения, придётся протестировать новый RC.

Если при тестировании были исправления, в итогах workflow появится ссылка для создания
PR **из релизной ветки в `main`**. Откройте PR по ссылке, получите approval и слейте
его с помощью **Create a merge commit**, не squash:
это сохраняет стабильный тег в истории `main` и не теряет релизные исправления.
Следующий выпуск блокируется, пока последний stable-коммит не входит в историю `main`.
Сохраняйте релизные ветки: они используются для проверки stable и исправлений.

## Права и ограничения

- `prepare` и `publish-stable` доступны только `qwer605` и `alx1115` и запускаются из `main`.
- Для `main` и `release/*` обязательны PR, чужой approval и review владельца кода.
- Теги `v*` защищены от изменения и удаления. Бот создаёт новые теги без обхода защиты веток.
- Тесты и экспорт работают с токеном только для чтения; секреты публикации им не передаются.
- Публикация выполняется отдельной задачей на коде контроллера из `main`.
- Используется встроенный `GITHUB_TOKEN`, отдельный PAT не нужен. Первый RC строится
  в том же запуске, поскольку созданная ботом ветка не запускает новый push-workflow.
- Разрешение GitHub Actions на создание/одобрение PR не требуется и не включается.
  Для возврата исправлений workflow выводит ссылку на создание обычного PR человеком.

Автотесты не заменяют ручную проверку графики, игрового ощущения и Windows-сборки.
Stable-публикация — явное подтверждение результата тестирования человеком.

## Если запуск упал

Исправьте причину и используйте **Re-run failed jobs**. Неполная публикация остаётся
черновиком, существующие теги не перемещаются. Повторная загрузка уже существующих
файлов допускается только при совпадении байтов. Повтор `prepare` для того же SHA
использует ту же ветку и кандидат. Если `main` уже изменился, продолжайте существующий
релиз через PR в релизную ветку.

Ссылку для PR с исправлениями можно повторно получить запуском `publish-stable`
для того же RC: опубликованные файлы проверяются и остаются прежними.

## Обновление инструментов

Версия движка хранится в `.godot-version`; экспортные шаблоны должны совпадать с ней.
Release Please закреплён в `.github/release/package.json` и `package-lock.json`.
Контроллер использует его парсер Conventional Commits и стратегию SemVer; обновление
пакета требует запуска тестов, поскольку эти API импортируются из `build/src`.
Действия GitHub закреплены по SHA коммита.
